# ano-mp's documents

What each document under `docs/` is for, who reads it, and whether it is
**current** (kept in step with the code, by a check where there is one)
or a **record** (history, moved here word for word when the work
finished, and not updated afterwards except to correct a mistake in the
move).

Where to look for what isn't here:

- **Building, running and testing the app**, its status and the
  repository's layout: [`README.md`](../README.md).
- **The rules each area of the code keeps** and the commands for each
  check: [`CLAUDE.md`](../CLAUDE.md).
- **The roadmap**: what is done, what is open, the decisions and why
  they were made, the risks and the release plan:
  [`PLAN.md`](../PLAN.md). Each finished phase there links to its
  record below.
- **A plan item's number** (H11, X6, D4…): the
  [index of plan items](plan-items.md).

Every document here is Markdown, and `check-docs.py` checks the paths
and links in all of them (anchors included); `check-mermaid.py` parses
their diagrams.

## For people who use the app

- [**User guide**](user-guide/README.md) (`user-guide/`, Phase 7c D1):
  how to use ano-mp, from the first run to every setting, with
  appendices for keyboard shortcuts, formats, a glossary and every error
  message. It assumes nothing about how the app is built, and the app
  bundles it (Help › ano-mp Help). *Current*: `check-user-guide.py`
  fails when a sidebar item, Settings section, feature switch, menu item
  or error message is missing, or the shortcuts appendix disagrees with
  the menus and the shortcuts sheet; its settings reference
  (`settings-reference.md`) is generated, and `guide.rs`'s test fails
  while it is stale. Its screenshots wait for the release build.

## For developers

- [**Developer guide**](developer-guide/README.md)
  (`developer-guide/`, Phase 7c D2): how the code is organised and works,
  for a developer new to it: the layers and threads, each part, worked
  sequences across the layers, the data, troubleshooting, testing,
  building, and recipes for common changes. Start with its overview;
  its [repository map](developer-guide/03-repository-map.md) finds the
  file behind a behaviour. *Current*: `check-developer-guide.py` fails
  when the repository map misses a module of the core, the effects, the
  Rust backend or the frontend, or names one that has gone; the rest is
  kept in step by hand, in the commit that changes what it explains.
- [**Porting**](developer-guide/14-porting.md)
  (`developer-guide/14-porting.md`, Phase 7c D4): the developer guide's
  chapter for whoever starts Phase 8, 9 or 10 (iOS and iPadOS, Linux,
  Windows): what is portable already, every macOS-only seam with its
  interface, fallback and what each OS needs, what the fallbacks lose,
  the build, bundle and CI steps per OS, and the recipe for adding a
  platform's implementation. *Current*: kept in step by hand with the
  platform files, `cfg`s and scripts it lists, like the rest of the
  guide; its paths and links are checked.
- [**Dictionary of classes and types**](class-dictionary/README.md)
  (`class-dictionary/`, Phase 7c D3): every named type, one page per
  layer (the C API, the core, the effects, the Rust backend, the
  frontend), alphabetical, with indexes by folder and from A to Z.
  The reference beside the developer guide. *Current*:
  `class-dictionary.py --check` fails on a type with no entry, an entry
  for a type that has gone, or a stale index.
- [**Index of plan items**](plan-items.md) (`plan-items.md`, Phase 7c
  D4): every numbered item of `PLAN.md` (O, F, H, X, D, N and M) with
  its name, status, the plan's section that defines it and its record
  here. For anyone who meets a number in the code, the docs or a commit.
  *Current*: generated by `plan-items.py` from the plan and the design
  notes; `plan-items.py --check` fails while it is stale. Don't edit it.
- [**Design records**](design/) (`design/`): how each phase was built,
  one file per phase from
  [Phase 0](design/phase-0-toolchain.md) to
  [Phase 7c](design/phase-7c-documentation.md): the designs, the steps as
  built, what was found and the known limits, in the order things
  happened. Read one to learn why something is as it is; the developer
  guide links to them rather than repeating them. *Records*: each was
  moved from `PLAN.md` word for word when its work finished (a whole
  phase, or one of Phase 7's steps and H items, Phase 7b's X items or
  Phase 7c's D items), and `PLAN.md` keeps the status, decisions and
  open items. Phase 7's and 7c's files still grow as more of those
  items finish.

## For the owner, at release

- [**Release decisions**](release-decisions.md): briefs for the
  decisions only the owner can make before the signed release (`PLAN.md`
  §8.1): the name and bundle identifier, distribution, the Apple
  Developer Program, the JUCE licence, AAC licensing, the privacy
  policy, MetaBrainz and crash reporting. Each says what is to decide,
  the options and what it blocks. *Current* while decisions are open;
  each decision is recorded, with its date, in `PLAN.md` §8.1, not here.
  No check beyond the links.
- [**Release smoke test**](release-smoke-test.md): the checks to run by
  hand on a clean Mac on each release's DMG before it is published
  (`PLAN.md` §8.3 and §8.7): download and first launch, the library,
  playback, online information, Phase 7b's features, an update from the
  previous version, performance and clean-up. Results go in `PLAN.md`.
  *Current*: kept in step by hand; a feature that ships gets a check
  here.
- [**Phase 7 Step 4 checklist**](step4-checklist.md): the exit checks of
  Phases 4–6c that only a sandboxed bundle shows, ordered by risk, each
  marked as a probe's or the owner's. The probe checks were done
  2026-10-02; the owner's (by ear, by eye or with hardware) wait.
  *Current* until those are done, then a *record*. Results go in
  `PLAN.md`'s Step 4 and in the checklist.
- [**Running a bundle check safely**](bundle-checks.md): how to run a
  sandboxed bundle without harming the owner's library, settings and
  folders in the real container: what to copy and move out first, how
  to run and probe it, and how to put everything back. For whoever runs
  one, and only after asking the owner (`CLAUDE.md`'s rule). *Current*.

## For reviewers

A reviewer of the §8.1 decisions, the security of the LAN remote or the
code in general starts with the [developer
guide](developer-guide/README.md)'s overview and repository map, then
the design record of the phase in question (the
[hardening record](design/phase-7-hardening.md) for security, the
sandbox and data protection). The release decisions above say what each
decision blocks.
