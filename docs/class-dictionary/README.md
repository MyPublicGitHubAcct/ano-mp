# Dictionary of classes and types

Every named type a developer meets in ano-mp, with what it is for: the C
API's types, the core's and the effects library's C++ classes, structs
and enums (public and private), the Rust backend's structs, enums and
traits, and the frontend's exported types, state modules and Svelte
components. Use it to look up a name you met in the code, or, through the
index below, to scan everything in one folder. The [developer
guide](../developer-guide/README.md) explains how the parts work
together; this dictionary is the reference beside it.

One page per layer, each in alphabetical order:

- [The C API](c-api.md): `core/include/anomp/anomp.h`.
- [The core](core.md): `core/src/` (C++).
- [The effects](effects.md): `effects/` (C++).
- [The Rust backend](rust.md): `app/src-tauri/src/`.
- [The frontend](frontend.md): `app/src/`.

## Reading an entry

Each entry is the type's name, then a line giving:

- its **kind**: a C++ class or struct, a Rust struct or trait, a TS type,
  a Svelte component and so on. "Sent to the UI" marks a Rust type the
  frontend receives (and has as a generated TypeScript type), "a setting"
  one stored in the settings. **Helper** marks a small private type,
  described in a line or not at all: listed so the dictionary is complete,
  not because it needs reading;
- its **file**, linked (two files when a type has a platform's
  implementation in each, or several modules share a private helper's
  name);
- the **thread** it lives on, where that matters (the engine and the
  queue on the main thread, the audio thread, a worker's own thread);
- a link to the **developer guide** section that explains it in context.

Then what it is responsible for, and its main collaborators: what owns or
calls it, and what it owns. Where the type has a doc comment, the entry
says the same thing; if they differ, the comment wins, and the entry
should be corrected from it.

## Keeping it current

`scripts/class-dictionary.py --check` (in `check-all.py`'s quick checks)
lists the types in the sources and compares them with the pages: a type
without an entry, an entry for a type that has gone, an entry without a
description (unless a helper), entries out of alphabetical order, a link
into the developer guide whose heading doesn't exist, or a stale index
below each fail it. When you add, rename or remove a type, change its
entry in the same commit, then run `scripts/class-dictionary.py` (without
`--check`) to rewrite the index. Test-only Rust code (`#[cfg(test)]`, and
modules declared under it) is left out.
